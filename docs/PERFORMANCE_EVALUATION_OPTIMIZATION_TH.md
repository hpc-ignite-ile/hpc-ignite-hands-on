# ทำให้งานเร็วขึ้น โดยยังได้คำตอบที่ถูกต้อง

การเพิ่มจำนวนคอร์ไม่ได้ทำให้ทุกโปรแกรมเร็วขึ้นเสมอ บางงานรออ่านไฟล์ บางงานต้องคุยกันระหว่างคอร์ และบางโปรแกรมใช้ได้เพียงคอร์เดียว เราจึงต้อง **วัดก่อน แล้วเปลี่ยนทีละอย่าง**

เริ่มจาก [ใบงานประมาณทรัพยากร](RESOURCE_ESTIMATION_WORKBOOK.md) หากไม่คุ้นคำสั่ง เปิด [คำอธิบาย Bash](BASH_COMMAND_REFERENCE_TH.md) ประกอบ

## 1. มีผลตั้งต้นไว้เปรียบเทียบ

รันข้อมูลเล็กที่มีคำตอบให้ตรวจได้ บันทึกขนาดข้อมูล รุ่นโปรแกรม จำนวนคอร์ เวลา และคำตอบไว้ นี่คือผลตั้งต้น ไม่ใช่รอบที่ต้องเร็วที่สุด

| รอบ | จำนวนคอร์ | เวลา (วินาที) | คำตอบถูกต้องหรือไม่ |
|---|---:|---:|---|
| 1 | 1 | กรอกหลังรัน | กรอกหลังตรวจ |
| 2 | 1 | กรอกหลังรัน | กรอกหลังตรวจ |
| 3 | 1 | กรอกหลังรัน | กรอกหลังตรวจ |

เวลารอคิวไม่ใช่เวลาคำนวณ และรอบแรกอาจเสียเวลาโหลดโปรแกรมหรือเตรียมข้อมูลมากกว่ารอบถัดไป จดแยกไว้

## 2. วัดเวลาสองแบบ

- **เวลาทั้งงาน:** ดู `Elapsed` และ `TotalCPU` จาก Slurm รวมการเริ่มโปรแกรมด้วย
- **เวลาเฉพาะส่วน:** จับเวลาส่วนอ่านข้อมูล คำนวณ และเขียนผล เพื่อรู้ว่าควรแก้ตรงไหน

ตัวอย่างบรรทัดสำหรับใส่ **ในไฟล์งาน Slurm** หลังโหลดโปรแกรมแล้ว:

```bash
result_dir="results/${SLURM_JOB_ID}"
mkdir -p "$result_dir"
/usr/bin/time -v -o "$result_dir/time.txt" \
    python src/main.py > "$result_dir/output.txt"
```

ใช้กับงาน Python กระบวนการเดียว และเปลี่ยนชื่อไฟล์ให้ตรงบทเรียน ถ้าเป็น MPI ให้ใช้คำสั่ง `srun` ตามบทนั้น สถิติของตัวเปิดงาน MPI ไม่ได้แทนหน่วยความจำรวมทุกกระบวนการ ให้ดูแถวขั้นงานใน `sacct` ประกอบ

## 3. ลองเพิ่มคอร์โดยไม่เพิ่มข้อมูล

**ตัวอย่างสมมติ:** คอร์เดียวใช้ 12 วินาที สี่คอร์ใช้ 4 วินาที จึงเร็วขึ้น 12 ÷ 4 = 3 เท่า ไม่ใช่ 4 เท่า

ประสิทธิภาพการแบ่งงานในตัวอย่างนี้คือ 3 ÷ 4 = 75% แต่ใช้ชั่วโมงคอร์มากขึ้น เพราะ 4 × 4 มากกว่า 1 × 12 คุณต้องเลือกว่าอยากได้คำตอบเร็วขึ้นหรือใช้ทรัพยากรรวมให้น้อยลง

เปรียบเทียบด้วยข้อมูล รุ่นโปรแกรม และความแม่นยำเท่ากัน ทำซ้ำอย่างละสามครั้ง อย่าเลือกเฉพาะรอบที่เร็วที่สุด

## 4. แต่ละบทควรลองเปลี่ยนอะไร?

| กลุ่มบทเรียน | สิ่งที่ลองเปลี่ยน | สิ่งที่ต้องตรวจ |
|---|---|---|
| งานแรกและตรวจโปรแกรม | ขนาดงานเล็กกับใหญ่ | เวลาเริ่มโปรแกรมอาจมากกว่าเวลาคำนวณ |
| CPU และชุดงานย่อย | จำนวนงานที่ทำพร้อมกัน | ทุกงานได้ผลครบและไม่ใช้พื้นที่ไฟล์มากเกินไป |
| MPI / OpenMP | 1, 2, 4 คอร์ด้วยข้อมูลเดิม | ผลรวมตรงกันภายในค่าคลาดเคลื่อนที่ยอมรับ |
| Dask / ข้อมูลตาราง | ขนาดส่วนข้อมูลและจำนวนผู้ทำงาน | ไม่สร้างงานย่อยเล็กเกินไปหรือใช้หน่วยความจำหมด |
| ภาพและข้อมูลแผนที่ | ความละเอียดหรือขนาดส่วนภาพ | ผลและหน่วยบนแกนยังถูกต้อง |
| GPU / AI | ขนาดชุดข้อมูลที่ส่งเข้าโมเดล | ความเร็ว หน่วยความจำ GPU และความแม่นยำ |
| คอนเทนเนอร์ | รันในและนอกคอนเทนเนอร์ | ใช้โปรแกรมและข้อมูลเท่ากัน |
| โมเลกุล | CPU กับ GPU หนึ่งตัว | พลังงาน อุณหภูมิ และจำนวนขั้นจำลอง |
| วัสดุ | จำนวนกระบวนการโดยคงความแม่นยำ | พลังงานลู่เข้าและใกล้กัน |
| ภูมิอากาศ / ของไหล | จำนวนช่องตาราง | ความละเอียดดีขึ้นแต่ขั้นเวลาอาจต้องเล็กลง |
| ชีวสารสนเทศ | จำนวนเธรดค้นหา | รายการและคะแนนค้นหาตรงกัน |
| Mesa / โรคจำลอง | จำนวนตัวแทนหรือจำนวนการทดลอง | ประชากรไม่หาย และใช้ค่าเริ่มสุ่มที่เปรียบเทียบกันได้ |
| อาคาร | ระยะเวลาจำลองหรือวิธีควบคุม | เวลาเชื่อมกันถูกต้องและค่าพลังงานมีเหตุผล |
| Jupyter | เวลาที่เปิดใช้งานจริง | ไม่จองเครื่องทิ้งไว้เมื่อเลิกใช้ |
| ความปลอดภัย / การเตรียมข้อความ | จำนวนไฟล์สมมติ | ไม่อ่านข้อมูลลับของผู้อื่น |
| พลังงานและคาร์บอน | วิธีที่ใช้เครื่องน้อยลง | ไม่เรียกชั่วโมงคอร์ว่าไฟฟ้าหรือคาร์บอนโดยไม่มีการวัด |

## 5. แก้สิ่งที่ช้าที่สุดก่อน

1. ลดการคำนวณที่ซ้ำโดยไม่จำเป็น
2. ลดการอ่านเขียนไฟล์จิ๋วจำนวนมาก
3. ใช้การคำนวณเป็นชุดแทนวนทีละรายการ เมื่อให้ผลเท่ากัน
4. จัดจำนวนกระบวนการกับเธรดให้พอดีกับคอร์ที่ขอ
5. เพิ่มเครื่องหรือ GPU เมื่อวัดแล้วว่าช่วยได้จริง

หยุดและตรวจปัญหาเมื่อคำตอบผิด หน่วยความจำไม่พอ หรือหมดเวลา อย่าเพิ่มทรัพยากรเป็นสองเท่าโดยยังไม่รู้สาเหตุ

## 6. สรุปให้คนอื่นเข้าใจ

รายงานสั้น ๆ ควรตอบได้ว่า ใช้ข้อมูลอะไร เปลี่ยนอะไร เร็วขึ้นเท่าไร ใช้ทรัพยากรเพิ่มหรือลด และตรวจคำตอบอย่างไร ภาพควรแสดงผลที่สำคัญ ไม่ต้องมีหน้าต่างคำสั่งหรือข้อความทั้งหมด

ถ้าใช้คลังโค้ดนี้ มี `scripts/summarize_performance.py` ช่วยสรุปไฟล์การทดลองได้ ดูรูปแบบคอลัมน์ด้วย `--help` ก่อนใช้ ตัวอย่างตัวเลขที่แต่งขึ้นเพื่อฝึกคำนวณต้องเขียนว่า “สมมติ” เสมอ
